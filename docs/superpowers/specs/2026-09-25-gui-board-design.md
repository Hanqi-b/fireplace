# 本机对战网页：战场式界面设计

状态：第二版视觉与交互稿已落实到运行中的本机 GUI；本文件记录设计依据。

## 目标与参考

以用户提供的 1680×928 对战截图作为**空间关系**参考：对手在上，我方在下，两排随从围绕中央战场，手牌贴近下边缘，结束回合位于右侧。画面四角是装饰场景，战场中央保持低干扰。采用原创的场景贴图、边框和控件，不把参考截图作为网页背景或切片。

第二版桌面预览见 [桌面战场](2026-09-25-gui-board-v2-desktop.png)，窄屏预览见 [窄屏战场](2026-09-25-gui-board-v2-mobile.png)；[可编辑 HTML/CSS 视觉稿](2026-09-25-gui-board-v2.html) 保留了各层的定位和样式。截图使用本机 `card_assets` 缓存里的真实卡牌图作示意；卡牌图没有复制进仓库。HTML 中的卡牌 URL 指向现有 `/assets/render/{card_id}`，正式页面继续使用现有资源请求与重试逻辑。直接用 `file://` 打开 HTML 时没有该资源路由，离线查看请以两张截图为准。

## 第二版视觉方向（依据 `ui-ux-pro-max`）

选用该技能检索到的 **3D / Hyperrealism 与 Skeuomorphism** 方向：木框、旧铜、石质桌面与魔法光源提供触感和层次。检索出的通用营销页布局与玻璃态建议不适合对战界面，未采用。画面保留经典奇幻卡牌对战的上下阵营、扇形手牌、椭圆肖像、右侧结束回合按钮和法力晶体，同时使用原创场景而不是复刻参考图。中文标题用本机 `Noto Serif CJK SC`，控件和数字用 `Noto Sans CJK SC`，无远程字体依赖。

唯一新增的美术资源是 [战场场景 WebP](assets/gui-board-scene.webp)（约 326 KB）。四角分别是星盘林地、冰霜泉、熔炉和奥术仪器；中间留白与横向分界线承载两排随从。场景图只在不可点击的底层，不能烘焙卡牌、英雄、按钮、数值或文字。角色和卡牌仍由 `Observation` 与现有 `AssetService` 生成，原有 CSS placeholder 是资源缺失时的退路。设计稿中的英雄、随从和手牌只是布局样例，不要求另做一套美术或替换现有 API。

交互强调三种强度：可行动来源为柔和绿色描边；当前合法目标为金色描边并有简短标签；提交成功后的伤害/治疗反馈使用短暂暖色/冷色闪光。静态纹理保留细节，但不在场面中央放动态背景。手牌比第一版预览放大约三成，悬停与键盘焦点使整张卡上移显露；点击和键盘也能完成所有操作，不把拖拽作为唯一入口。动画需遵守 `prefers-reduced-motion`。

颜色基准为胡桃木 `#332419`、旧金 `#C99B53`、羊皮纸 `#E8DFCA`、冷石 `#5B5B70`、法力蓝 `#80CAFF`、合法来源绿 `#78DB74`、目标金 `#F4BA59`、受伤红 `#E26B57`。文字放在有遮罩的木/石牌匾上，不能直接叠在复杂贴图上；小字号与背景保持可读对比，焦点轮廓始终可见。

## 页面层级

1. **首屏战场**：占据桌面视口的主要区域；对手暗手在上缘，双方英雄、技能与随从在战场内，我方手牌沿下缘展开。武器固定在所属英雄左侧，显示攻击与耐久，不能占随从槽；右侧是结束回合与法力，边缘可放牌库、奥秘及简短阶段提示。没有独立的大型信息面板。
2. **当前决策层**：平时只显示合法来源的弱提示。点选来源后，在战场中显示目标高亮、插入站位或分支选择。结束回合在右侧；卡牌、角色与英雄技能可直接点击。
3. **屏幕下方的辅助区**：公开对局记录、出牌/攻击/英雄技能的备用快捷入口和“全部合法动作（备用）”位于战场之后的页面流中。完整动作列表默认折叠，不能覆盖战场；日志可展开浏览。版本号、连接详情等调试信息也放在这里。底部辅助区是普通页面流，允许滚动，战场内不出现调试面板。
4. **阶段覆盖层**：Mulligan 在我方手牌前显示选中/保留和确认；Choice/Discover 居中展示可选卡牌；Game Over 在战场上显示结果，同时允许查看原战场和下方日志。覆盖层保留关闭、确认、错误反馈的清晰位置。

## 布局与尺寸约束

桌面以 16:9 战场为基准，最大宽度约 1680 CSS 像素，按可用视口缩放；重要角色和按钮用布局容器定位，不把整个交互层烘焙进一张大图。场景图允许在四边裁切，装饰层设置 `pointer-events: none`。中央战场不放说明文字，交互控件位于更高的层级。

在 1280×720 和 1440×900 下，战场的英雄、两排七个随从、十张手牌、结束回合与法力都要可达。手牌可扇形重叠，但 hover/焦点时必须完整显露，不能被战场裁切。卡牌容器保留自己的堆叠层级与滚动/平移空间；宽度不足时只让手牌区域滚动，不让整页横向溢出。结束回合与主要角色目标至少有 44×44 CSS px 的有效触控区。

小于约 760 CSS 像素时切为窄屏排布：保留“对手上、我方下”的顺序，四角装饰裁切为细边，手牌变成横向卡牌带，动作提示收为紧凑条；日志和备用动作仍在战场下方。窄屏不强行缩放整块 16:9 战场，否则卡牌文字与目标区域会过小。移动端选择卡牌后用可点击的放大卡面读全文，目标和站位仍能点击。支持浏览器 125%/150% 缩放、触控点击和减少动态效果设置。

## 组件与数据映射

| 界面区域 | 唯一数据来源 | 表现 |
| --- | --- | --- |
| 对手暗手 | `observation.opponent.hand_count` | 只绘制卡背数量，不读取对手卡牌对象或卡 ID |
| 双方英雄、技能、武器、奥秘、法力、牌库 | Observation 中的公开字段与 `self` 字段 | 数值独立覆盖在卡图/头像上；不存在的字段隐藏 |
| 两排随从 | `self.board`、`opponent.board` | 用 `entity_id` 保持节点身份；最多七个位置；显式标出可攻击与合法目标 |
| 我方手牌 | `self.hand` | 完整卡牌图、费用、名称；放大时独立显示可读文本 |
| 出牌、攻击、技能、结束回合、换牌、选择 | 当前 `legal_actions` 的原始 Action | 界面只筛选与选择 Action，不拼造游戏命令；提交仍带 `session_id` 和 `revision` |
| 卡名、卡文、卡图 | 服务器 enrich 的名称/文本与本机 `/assets/...` | 手中/放大使用 `render`，场面优先尝试 `tile`/`art`；缺失时使用可读占位 |
| 场景四角、战场底纹 | `web_gui/board-scene.webp` 本地静态贴图 | 不经过卡牌 `AssetResolver`；资源缺失时退回 CSS 背景 |

卡牌资源继续使用仓库外缓存。浏览器只向本机服务请求图片，不自行访问外部卡牌站点。场景贴图通过网页静态资源路由提供，且不含任何游戏状态。

## 决策与状态同步

交互状态为：未选来源 → 已选来源 → 分支/站位/目标选择 → 提交中 → 新快照。Mulligan、Choice、AI 行动中、过期动作、Game Over 各有独立呈现。任何阶段变化或 `revision` 更新都重新核对当前选择是否仍在 `legal_actions` 中；旧目标高亮和旧插入槽立即撤销。409 过期响应使用返回的新快照，显示短提示并让玩家重新操作。

视觉层按 `entity_id` 保留稳定节点，使攻击线、伤害、召唤和治疗反馈能够从前一快照过渡到后一快照。第一轮改造只使用现有公开事件和快照差分；如果以后需要逐个展示连锁效果，再定义最小的公开事件 DTO，不让网页接触 `Game`、`Player` 或 `Card` 对象。

## 工作顺序与边界

1. 先确定桌面/窄屏视觉稿及层级，明确贴图留白、真实卡图比例和按钮尺寸。
2. 再拆分现有前端的状态同步、战场组件、交互层与反馈层；保留 `/api/state`、`/api/action` 和原始 Action 边界。
3. 先替换布局与静态表现，再接回所有交互；场景贴图和卡牌素材可以与组件开发并行准备。
4. 在真实对局测试通过前，不移除现有备用动作入口。

实现仍不编辑 `fireplace/controller.py`、`agent_api.py`、`observation.py` 或游戏规则。职业/套牌选择与重开属于后续独立的开局流程，不在这次战场布局设计内。

## 已完成的验收

- 桌面和窄屏预览均能指出所有现有信息与操作的落点，包括英雄、技能、场面、手牌、目标、站位、Mulligan、Choice 和结束回合。
- 武器贴附在英雄区左侧，随从排不包含武器；手牌在桌面与窄屏均可读，放大时完整显露。
- 四角场景贴图与中央可点击区域分层明确；参考图不会直接进入产品资源。
- 对手暗手、原始 Action、过期动作和本地资源边界有明确处理。
- 英雄与卡牌无需另做美术，现有 API 图片被复用；外部图片缓存不进入仓库。
- 视觉稿已落实到正式 `index.html`、`style.css`、`app.js`；交互状态在前端通过独立于 DOM 的 `createGuiState()` 管理。
- Python 接口测试、真实引擎浏览器交互测试与 Random/Heuristic 两场完整浏览器对局均通过；桌面和窄屏截图已人工检查。
